# 静态图片迁移缓存修复

## 证据和范围

用户截图中，英文首页四个产品分类均出现真实裂图。当前服务器的同路径文件均能完整下载、解码；Chrome、WebKit、中文移动视口及 1Mbps 限速测试均正常。

2026-11-02 实测：旧 Cloudflare NS 仍返回旧站 198.202.211.1；当前注册局与阿里云权威 NS 为 dns17/dns18.hichina.com，公开递归解析返回 177.5.75.237。指定旧 IP 请求同一图片地址，得到 `404`、`text/html`、`Cache-Control: public, max-age=432000`（五天）。新服务器返回正确图片与一天成功缓存。

使用本地透明代理、真实 Chrome HTTP 缓存、旧站真实 404 响应复现：缓存旧错误 → 换新上游而 URL 不变 → 四图仍裂且不发上游请求 → 添加稳定版本参数 → 四图下载及解码成功。这是经验证的故障机制，不代表已读取或证实用户浏览器里的具体缓存条目。

## 修复选择

采用静态图片 URL 版本化，主动绕开迁移前的负缓存。仅修改站内 `/media/` 图片，保留文件本身、布局、懒加载、动态效果及 GitHub Pages basePath；后台 `/uploads/` 的 UUID、外部 URL 不改。不修改 DNS，不访问原 Cloudflare 账号，不购买服务，不清除用户 Cookie 或后台会话。

不采用清除全站浏览器数据：无法覆盖旧缓存拦截的请求，且无须触及登录状态。不采用无限重试或图片改指向固定 IP：不能可靠绕过负缓存，并引入额外连接与运维依赖。

版本参数固定为 `apower_v=20261102`，不可按每次请求时间生成。保留原查询参数与 hash，重复调用不叠加版本参数。未来同名素材替换仍按原约定更名或显式升级版本。

## 验证和发布

先增加会在旧实现失败的浏览器负缓存回归，再实现最小修复，验证单元测试、类型检查、生产构建和完整本地浏览器测试。独立审查后，以新 release 暂存、只读验证、可回退切换发布；后台数据库、上传、环境文件不变。发布后重新验证缓存复现场景和正式站四张图。
